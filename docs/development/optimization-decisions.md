# Optimization decisions

Jev helped identify these leads. The decisions below use production code,
profiles, and benchmark results. Reopen a lead when new evidence meets the
stated condition. Another review pointing to the same code is insufficient.

| Candidate | Decision and evidence | When to reopen |
| --- | --- | --- |
| Cache SST V5 restart boundaries | Closed. The full decoder cache and the smaller point-lookup cache both failed to show a repeatable throughput gain. Three paired comparisons and four closer-spaced in-memory pairs tested the smaller cache. The builds decoded the same entries, and the in-memory benchmark and malformed-boundary regression landed independently. [#1126](https://github.com/cntryl/midge/issues/1126) · [#1134](https://github.com/cntryl/midge/pull/1134) | A profile attributes material CPU time to the repeated restart-word loads themselves, and a matched comparison reproduces a gain on that workload. |
| Share block-backed values from the raw SST cursor | Deferred. The compaction profile at `e07675f7` showed block decompression and memory reservations prominently. Samples under raw-cursor copying did not isolate a material cost for the value copy alone. The cursor releases its decompressed-block reservation on advance, so shared slices would require charging full pinned blocks through the merge heap and key groups. Owned values keep that retention proportional to the yielded values. | A large-value or high-fan-in workload measures value materialization as a material cost, and a candidate shows lower CPU with bounded peak retained bytes across block and budget boundaries. |
| Avoid the streaming SST scratch-to-output copy | Deferred. The streaming writer reads its finalized scratch file through the write-rate limiter and persists the SST with its size and CRC32C receipt. The available measurements do not isolate that pass as the limiting cost. Removing it requires preserving rate accounting, publication and sync ordering, and scratch cleanup. | Stage-attributed compaction measurements show that this second pass limits throughput or drives material write amplification on a representative storage backend. |
| Avoid concatenating queued WAL writes | Deferred. The writer already takes ownership of the buffer for a single queued write. Concatenation occurs only for batches with several queued writes. The available evidence does not show that this copy dominates encode, append, or sync under strict commits. | WAL phase data and batch-size observations show that multi-entry coalescing consumes material CPU or tail latency. Any candidate must preserve offsets and partial-write and retry semantics. |
